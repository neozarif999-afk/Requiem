# Freelance Expert Projects

Turns freelance/online-work requests into two things clients pay for:
a **deliverable** that reads like it came from a specialist, and the
**packaging** (proposal, gig listing, portfolio piece) that gets it hired.
Treat every output as a portfolio sample — it should be reusable as proof
of skill, not just a one-off answer.

Reference files with copy-paste templates and platform specifics:
- `reference/platforms.md` — where to find work, by category, with what to
  optimize on each platform.
- `reference/proposal-templates.md` — proposal, cold-pitch, and gig-listing
  templates.

Read the relevant reference file before drafting a proposal or gig listing —
don't improvise from memory.

## Core principle

Generic output loses to specific output. A client (or a hiring algorithm)
can tell in one paragraph whether a piece was tailored to them or is a
reskinned template. Every deliverable below should show: this was made
*for this brief*, using *real specifics* (numbers, names, constraints),
not filler. Never pad length with restated headers, throat-clearing intros,
or vague claims — see the `humanizer` skill if the draft is starting to
read AI-flavored.

Never fabricate stats, testimonials, credentials, or client results to pad
a portfolio or proposal. If a portfolio needs a sample and there's no real
client work yet, build a clearly-labeled spec/demo project — don't disguise
it as paid client work.

## Part 1 — Article & content writing

**Match structure to type before writing:**

| Type | Structure | Length |
|---|---|---|
| SEO blog post | Hook → problem → structured H2 sections answering search intent → FAQ → CTA | 800–2000 words |
| Listicle | Intro (what/why) → numbered items, each with a concrete takeaway → closer | 600–1500 words |
| How-to/tutorial | Prereqs → numbered steps, each independently testable → troubleshooting → recap | Varies |
| Thought-leadership/opinion | Claim → evidence/experience → counterargument acknowledged → conclusion | 800–1200 words |
| Product/technical copy | Feature → benefit → proof (spec, number, use case) | Tight, scannable |
| News/press-style | Lede with the actual news in sentence 1 → context → quotes/detail → background | Inverted pyramid |

**Workflow:**
1. Extract the brief's real constraints: audience, intent (inform/convert/
   rank), keyword or angle, tone, word count, any facts/sources supplied.
2. Outline headers before drafting; check the outline actually answers
   what the target reader searched or asked.
3. Draft with specifics — real numbers, named tools/examples, concrete
   claims — not "many businesses find that...".
4. If SEO is in scope: one primary keyword in title/H1/first 100 words,
   related terms worked in naturally, meta description under 160 chars,
   internal/external link slots marked for the client to fill.
5. Edit pass for AI-tells (puffery, formulaic transitions, compulsive
   summaries) — invoke the `humanizer` skill for this pass on longer pieces.
6. Never invent quotes, statistics, or sources. Mark `[VERIFY]` on any
   claim you can't confirm rather than smoothing over it.

## Part 2 — Website design

**Match scope to the ask:**

| Site type | Core sections | Notes |
|---|---|---|
| Landing page | Hero + value prop, social proof, features/benefits, CTA, footer | One conversion goal only |
| Portfolio | Hero, selected work (3–6 pieces with context, not just images), about, contact | Work samples > text about yourself |
| Small business site | Home, services, about, contact, (blog if content marketing matters) | Must work perfectly on mobile |
| E-commerce | Home, category/listing, product detail, cart/checkout, account | Trust signals near price/CTA |

**Workflow:**
1. Confirm: audience, primary action wanted, brand assets (colors/logo/
   fonts) available or need to be chosen, and platform constraint (custom
   code, WordPress, Webflow, Shopify, etc.) — don't build in a stack the
   client can't maintain.
2. Wireframe the layout in words or ASCII before styling: what's above the
   fold, what's the one CTA per section.
3. Build mobile-first. Check contrast and tap-target size, not just desktop
   aesthetics.
4. Use the `dataviz`/`artifact-design` skills' visual-design instincts
   (hierarchy, spacing, restrained palette) even outside a chart context —
   same principles apply to page layout.
5. Ship with basics a client will ask about even if unprompted: page title/
   meta description, alt text on images, a favicon, and that forms/links
   actually work — test the golden path in a browser before calling it done.

## Part 3 — Other online jobs

Don't default to "article + website" for every ask — match the deliverable
to what the gig actually is:

- **Virtual assistant**: inbox/calendar triage templates, SOP documents,
  task trackers. Deliverable is a repeatable process, not a one-off.
- **Data entry / research**: a clean, validated spreadsheet with a documented
  source for every row — never fabricate a row to fill a gap.
- **Transcription/captioning**: verbatim vs. clean transcript — confirm
  which before starting; timestamp at speaker changes.
- **Social media management**: a content calendar (day, platform, copy,
  visual note, CTA) plus 3–5 sample posts in the client's actual voice.
- **Graphic design (non-web)**: match the brief's usage (print vs. digital,
  dimensions/bleed, file formats the client's tools accept).
- **Translation/localization**: preserve meaning and tone over literal
  wording; flag idioms with no clean equivalent instead of guessing.
- **Voiceover/audio editing**: deliver in the format/sample-rate requested;
  note any script line that reads awkwardly aloud.

For anything outside these, ask what the actual deliverable and acceptance
criteria are before producing work — "online job" descriptions are vague
by default; the paid version isn't.

## Part 4 — Finding the work

See `reference/platforms.md` for the platform-by-category breakdown and
`reference/proposal-templates.md` for ready templates. In brief:

1. **Pick 2–3 platforms** matching the service (see reference) — spreading
   thin across every platform dilutes the profile/rating that makes clients
   trust a new freelancer.
2. **Profile/gig page**: lead with the client's outcome, not a list of
   skills ("I write SEO blog posts that rank" beats "Experienced writer").
   Show 2–3 real or spec samples.
3. **Proposals**: reference something specific from the job post in the
   first line, state the concrete plan (not just "I can do this"), and
   end with one clarifying question — it invites a reply.
4. **Pricing**: price the outcome/scope, not just hours, once there's
   enough track record to do so; until then, competitive-but-not-lowest
   hourly/fixed rates plus fast, high-quality delivery build the first
   reviews that let pricing go up.

## Part 5 — Doing it easily (systemize repeat work)

- Keep a personal swipe file of outline templates per content type (Part 1
  table) and page-section templates per site type (Part 2 table) — reuse
  the structure, never reuse client-specific copy across clients.
- Keep a running FAQ/checklist per service so scoping a new job takes
  minutes: required inputs, standard deliverable format, standard revision
  count.
- Batch similar tasks (all outlines, then all drafts, then all edits)
  rather than finishing one article start-to-finish before starting the
  next — this is where most of the speed gain comes from at volume.
- Track turnaround time and client feedback per job; feed recurring
  feedback back into the templates above instead of relearning it each time.

## Output expectations

When asked to produce a deliverable, produce the actual deliverable (the
article, the page, the spreadsheet) — not a description of what a
deliverable would contain. When asked to help find work, produce the
actual proposal/gig text ready to send, tailored with the specifics given.
If specifics are missing (word count, platform, brand assets, budget),
ask rather than inventing them silently.
